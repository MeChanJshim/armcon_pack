# Y2SYS_ID

`Y2SYS_ID` applies Cartesian excitation through `Y2RobMotion` and records the resulting simulated robot response for system identification.

The package is intended for this chain:

```text
/ur10skku/cmdMotion Cartesian command
  -> Y2RobMotion Position mode
  -> IK target joint generation
  -> /armsimul/joint_position_cmd_array
  -> armsimul_pack MuJoCo joint position actuator
  -> /ur10skku/currentP, /ur10skku/currentJ, /armsimul/joint_states
```

This identifies the closed-loop Cartesian command tracking behavior of the full software/simulation path. It is not only the bare MuJoCo joint actuator bandwidth.

## Nodes

### `cartesian_excitation_node`

Publishes excitation commands to `Y2RobMotion`.

Inputs:

- `/ur10skku/currentP` (`std_msgs/Float64MultiArray`): current Cartesian pose `[x, y, z, wx, wy, wz]`.

Outputs:

- `/ur10skku/cmdMode` (`std_msgs/String`): publishes `"Position"` during startup.
- `/ur10skku/cmdMotion` (`std_msgs/Float64MultiArray`): Cartesian target pose.

Behavior:

- Waits until a current pose is received.
- Stores the first received current pose as a fixed baseline.
- Adds a step, sine, or chirp offset to one selected Cartesian axis.
- Sends the full 6D pose command at `publish_rate_hz`.

Units:

- `x`, `y`, `z`: millimeters, following `Y2RobMotion`.
- `wx`, `wy`, `wz`: radians.

### `response_recorder_node`

Records command, target, measured Cartesian/joint response, actuator effort, and wrench to CSV.

Subscribed topics:

- `/ur10skku/cmdMotion`
- `/ur10skku/currentP`
- `/ur10skku/targetP`
- `/ur10skku/currentJ`
- `/ur10skku/targetJ`
- `/armsimul/joint_states`
- `/armsimul/ee_wrench`

Output:

- CSV files in `results/` by default.
- Vector fields are stored as semicolon-separated values inside quoted CSV cells.

Important fields:

- `command_pose`: command generated by `Y2SYS_ID`.
- `current_pose`: Cartesian response computed by `Y2RobMotion` from current joints.
- `target_joint`: IK target sent downstream by `Y2RobMotion`.
- `joint_state_effort`: MuJoCo actuator torque from `/armsimul/joint_states.effort`.

### `online_metrics_node`

Prints quick tracking metrics during the experiment.

Metrics:

- RMS Cartesian tracking error on the selected axis.
- Peak absolute Cartesian tracking error on the selected axis.

This node is only for live monitoring. Use `scripts/analyze_cartesian_id.py` for offline analysis.

### `system_id_node`

Computes a first-pass system identification result automatically at the end of the experiment.

This node is **not a controller**. It does not publish commands and does not change robot motion. It only subscribes to command/response topics, computes ID metrics, writes a YAML result, and exits so the launch file can stop the experiment.

Subscribed topics:

- `/ur10skku/cmdMotion`
- `/ur10skku/currentP`

Output:

- YAML result file in `results/`.

The node uses the configured timing:

```text
pre_hold_sec + duration_sec + post_hold_sec + finish_margin_sec
```

After this time, it writes ID metrics and exits. The launch file uses this node exit to shut down the full `Y2SYS_ID` launch.

Currently estimated metrics:

- common tracking summary: sample count, command span, response span, span gain, mean command/response, mean error bias, raw error, bias-corrected error
- sine input: amplitude gain and phase lag at `frequency_hz`
- sine sweep input: gain/phase per frequency, -3 dB bandwidth estimate, approximate second-order fit
- step input: steady-state error, overshoot, 10-90 percent rise time
- chirp input: tracking summary only for now

### `scripts/analyze_cartesian_id.py`

Offline CSV summary tool.

It reads one CSV, extracts `command_pose[axis]` and `current_pose[axis]`, and prints:

- sample count
- duration
- command span
- response span
- span gain
- RMS error
- peak absolute error

## Configuration

Default parameters are in:

```text
config/cartesian_id.yaml
```

Main parameters:

```yaml
excitation_type: "sine_sweep"   # step, sine, sine_sweep, chirp
axis: "z"                 # x, y, z, wx, wy, wz
amplitude: 5.0            # mm for x/y/z, rad for wx/wy/wz
frequency_hz: 0.5
frequencies_hz: [0.1, 0.2, 0.5, 1.0, 2.0]
cycles_per_frequency: 6.0
chirp_start_hz: 0.1
chirp_end_hz: 5.0
pre_hold_sec: 2.0
duration_sec: 20.0
post_hold_sec: 2.0
publish_rate_hz: 1000.0
```

For `sine_sweep`, `duration_sec` is computed automatically:

```text
duration_sec = sum(cycles_per_frequency / frequency_hz)
```

With the default sweep, active excitation time is:

```text
6/0.1 + 6/0.2 + 6/0.5 + 6/1.0 + 6/2.0 = 111 s
```

Use small amplitudes first. Cartesian commands are converted by IK, so large commands can cause joint-limit or IK behavior to dominate the identification result.

## Timing And Communication Rates

System identification depends on the timing of every loop in the chain. The default setup is intended to run at 1 kHz end to end:

```text
Y2SYS_ID command publish       1000 Hz  -> /ur10skku/cmdMotion
Y2SYS_ID CSV record            1000 Hz  -> response_recorder_node
Y2RobMotion control loop       1000 Hz  -> control_period = 0.001 s
armsimul_pack simulation       1000 Hz  -> simulation_rate_hz
armsimul_pack state publish    1000 Hz  -> publish_rate_hz
```

Relevant files:

```text
Y2SYS_ID/config/cartesian_id.yaml
  publish_rate_hz: Cartesian command publish rate to Y2RobMotion
  record_rate_hz: CSV logging rate

Y2RobMotion/config/y2_rob_motion.yaml
  control_period: Cartesian command, IK, and joint command loop period

armsimul_pack/config/ur10_contact_sim.yaml
  simulation_rate_hz: MuJoCo stepping rate
  publish_rate_hz: /armsimul/joint_states and /armsimul/ee_wrench publish rate
```

For clean identification, keep these rates aligned unless the experiment intentionally studies communication-rate effects. If one rate is lower than the others, the measured bandwidth and phase lag will be limited by that slower rate.

Recommended starting point:

```text
Y2SYS_ID publish_rate_hz       = 1000.0
Y2SYS_ID record_rate_hz        = 1000.0
Y2RobMotion control_period     = 0.001
armsimul_pack simulation_rate  = 1000.0
armsimul_pack publish_rate     = 1000.0
```

With 1 kHz sampling, start Cartesian sine/chirp tests conservatively, for example 0.1 Hz to 20 Hz. The theoretical Nyquist limit is much higher, but robot motion, IK behavior, actuator limits, and phase lag usually become the practical limits first.

## Build

From the workspace root:

```bash
cd /home/jay/armcon_ws
colcon build --packages-select Y2SYS_ID
source install/setup.bash
```

## Run Sequence

Terminal 1: start the MuJoCo simulator.

```bash
cd /home/jay/armcon_ws
source install/setup.bash
ros2 launch armsimul_pack ur10_contact_sim.launch.py
```

Terminal 2: start `Y2RobMotion` connected to the simulator.

```bash
cd /home/jay/armcon_ws
source install/setup.bash
ros2 launch Y2RobMotion ur_mujocoArm.launch.py
```

Terminal 3: start the identification experiment.

```bash
cd /home/jay/armcon_ws
source install/setup.bash
ros2 launch Y2SYS_ID cartesian_id.launch.py
```

The excitation node will publish `"Position"` to `/ur10skku/cmdMode`, wait for `/ur10skku/currentP`, then publish Cartesian excitation to `/ur10skku/cmdMotion`.

With the default `sine_sweep` timing, the launch runs for:

```text
pre_hold_sec      2.0 s
duration_sec    111.0 s
post_hold_sec     2.0 s
finish_margin     0.5 s
total           115.5 s
```

At the end, `system_id_node` writes a YAML result and the launch shuts down automatically.

## Offline Analysis

After an experiment:

```bash
ros2 run Y2SYS_ID analyze_cartesian_id.py \
  /home/jay/armcon_ws/src/armcon_pack/Y2SYS_ID/results/cartesian_id_YYYYMMDD_HHMMSS.csv \
  --axis z
```

The launch also writes an automatic ID YAML file:

```text
results/cartesian_id_id_YYYYMMDD_HHMMSS.yaml
```

The Python script is still useful for re-checking CSV files or testing different axes after the run.

The YAML reports both raw and bias-corrected tracking error:

```text
mean_error_bias = mean(command - response)
rms_error_raw = sqrt(mean((command - response)^2))
rms_error_bias_corrected = sqrt(mean((command - response - mean_error_bias)^2))
```

Use `mean_error_bias` to see how much DC offset exists between command and response. The sine and sine-sweep gain/phase calculations also remove the local mean before Fourier analysis, so bandwidth and second-order estimates are based on the oscillatory response rather than the DC offset.

## Recommended Experiments

Step response:

```yaml
excitation_type: "step"
axis: "z"
amplitude: 5.0
duration_sec: 5.0
```

Single-frequency sine:

```yaml
excitation_type: "sine"
axis: "z"
amplitude: 3.0
frequency_hz: 0.5
duration_sec: 20.0
```

Chirp:

```yaml
excitation_type: "chirp"
axis: "z"
amplitude: 2.0
chirp_start_hz: 0.1
chirp_end_hz: 5.0
duration_sec: 30.0
```

Sine sweep for bandwidth and second-order fitting:

```yaml
excitation_type: "sine_sweep"
axis: "z"
amplitude: 3.0
frequencies_hz: [0.1, 0.2, 0.5, 1.0, 2.0, 3.0, 5.0]
cycles_per_frequency: 6.0
settling_cycles: 1.5
```

For each frequency, the first `settling_cycles` are excluded from gain/phase estimation. The YAML result includes per-frequency gain/phase, estimated -3 dB bandwidth, and a rough second-order fit:

```text
estimated_bandwidth_hz
estimated_natural_frequency_hz
estimated_natural_frequency_rad_s
estimated_damping_ratio
estimated_delay_sec
```

## Topic Check

Useful checks:

```bash
ros2 topic echo /ur10skku/ctlMode
ros2 topic echo /ur10skku/currentP
ros2 topic echo /ur10skku/targetP
ros2 topic echo /ur10skku/currentJ
ros2 topic echo /armsimul/joint_states
```

`/armsimul/joint_states.effort` contains the MuJoCo actuator torque for each joint.
